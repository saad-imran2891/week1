Ranking Content for Refresh Review Across FlyRank's Full Client Warehouse

Abstract

Which existing pages should be prioritized for refresh review, and does a validated scoring model beat a transparent hand-rule baseline at full warehouse scale? We extended FlyRank's reference pipeline — feature engineering, a rule-based baseline, and a client-holdout-validated classifier — from a 30k-page teaching sample to the full ~79M-row search performance warehouse (104 clients, trailing 90-day window). At this scale, 90.1% of pages were labeled "declining" under the reference definition, which makes Precision@50 uninformative (it saturates near 1.0 regardless of model skill); ROC AUC is reported instead as the primary comparison metric. The best model (random forest) reached ROC AUC 0.743, while the hand-rule baseline scored 0.231 — worse than random guessing. The resulting ranked, reason-coded queue (149,497 pages) is offered as a reviewer aid, not an automatic publishing decision, with 74,467 pages flagged for refresh and only 17,546 at high confidence.

Introduction / Problem Statement

A content team with limited refresh-review capacity per cycle needs a prioritized, explainable queue rather than reviewing every page or relying on gut feel. FlyRank's reference pipeline (feature engineering → rule-based baseline → trained classifier → ranked, reason-coded output) already demonstrates this approach works on a curated 30k-page sample. This capstone tests whether the same pipeline, unmodified, holds up when applied to the full client base and its full data volume — which surfaces real-world messiness (incomplete recent data, an extremely skewed label distribution) that the curated sample didn't expose.

Data

  • Source: FlyRank internship warehouse (Hugging Face, gated) — dim_clients.parquet, dim_content.parquet, fact_content_daily_performance/ (partitioned by month, ~79M rows)
  • Not used: fact_content_query_90d.parquet — the model's feature set doesn't consume query-mix features, and that table's fixed 90-day window creates a leakage risk against a trailing-window label; left out as a documented gap rather than assumed safe
  • Window: trailing 90 days ending at (global max report date − 5 days), split into last-30d/prev-30d for the trend label. The 5-day pullback was added after diagnosing incomplete recent data: the number of distinct content items reporting any row per day dropped ~15% for the final 5 days versus the preceding 10, while aggregate impressions stayed flat — consistent with ingestion lag affecting smaller content items disproportionately
  • Volume floor: rows with prev-30d impressions below 20 are excluded before trend labeling (not part of the original reference pipeline). At full scale, median prev-30d impressions was only 5 before this floor — the trend percentage was dominated by tiny-denominator noise (e.g. a swing from 1 to 0 impressions computes as "-100%," indistinguishable from a real 50,000-to-0 collapse)
  • Per-client filter: only dates on/after each client's own GSC data start (unbalanced panel — history depth varies by client; some clients have no recorded start, handled as no restriction rather than exclusion)
  • GA4/GSC filters: each metric family summed only where its own availability flag is true (not simply "not false," since these can be null)
  • Average position: reconstructed as a weighted average from a daily position sum divided by daily impressions, since the raw table stores a sum, not a pre-averaged value
  • Content age / freshness: derived as date differences from content creation and last-optimized dates to the snapshot cutoff — using "last optimized" as "last updated" is an assumption, not a verified equivalence
  • Exclusions: 90-day impressions greater than 0, and content age at least 90 days, matching the reference pipeline
  • Public-safe: only pseudonymous content/client identifiers used throughout; no domains, URLs, or client names appear anywhere in this analysis or its outputs

Methodology

  • Label: a page is "declining" if its last-30d impressions fell more than 20% versus the prior 30 days
  • Leakage check: the trend direction and trend percentage are excluded from the model's feature set — they're the label source, never a feature
  • Baseline: a transparent hand-rule score — 40% visibility + 30% freshness risk + 25% position opportunity + 5% depth gap (no training)
  • Model: logistic regression, decision tree, and random forest; evaluated on a client-holdout split — entire clients held out of training, not random rows, so no client's own pages leak across the split
  • Metric switch: the reference pipeline selects by Precision@50, but at this dataset's 90.1% positive rate, Precision@50 saturates near 1.0 for nearly every scorer, including the baseline, and stops distinguishing model quality. ROC AUC is reported as the primary metric instead
  • Schema corrections made during this analysis: the raw warehouse uses separate pseudonymous client/content identifiers, separate GSC/GA4 availability flags, and a per-day position sum rather than a pre-averaged position column

The trained models substantially outperform the hand-rule baseline at ranking which pages are declining (best ROC AUC 0.743 vs. baseline 0.231 — worse than random). Precision@50 is uniformly near 1.0 across models and the baseline and is not treated as evidence of model skill here; it reflects the extreme base rate, not ranking quality. This result does not replicate the roughly 3x Precision@50 lift reported on the smaller, more balanced 30k-page teaching sample (54% declining there vs. 90% here) — the two aren't directly comparable because the underlying base rates differ so much.

Limitations & Honest Framing

  • Directional/associative, not causal — this model finds pages whose trailing-window features are associated with a declining trend label; it makes no claim about why a page is declining, and no claim whatsoever about Google's ranking algorithm
  • The 85–90% declining rate at full warehouse scale is far higher than the bundled sample's 54% and did not resolve after two independent adjustments (a minimum-volume floor and trimming an incomplete final-days tail) — each moved the rate by only a few percentage points. This is reported as an observed, unresolved feature of this snapshot's trend labels, not something traced to a specific cause
  • Precision@50 is uninformative at this base rate; ROC AUC is used as the primary comparison metric instead, but it doesn't tell you how well the model does at the specific "top 50" or "top N" sizes a reviewer would actually act on
  • Unbalanced panel: client history depth varies, and some clients carry entirely missing access flags. The exact count of clients/rows excluded by the 90-day filter was not separately measured in this analysis
  • Position-tier medians need a stated volume floor — a top-3 page with ~50 impressions/90d isn't comparable to one with 30,000; this analysis did not separately verify whether its position-tier distribution shows this skew
  • "Last updated" is derived from a proxy field, an assumption that wasn't independently verified against how the organization actually tracks content updates
  • Query-mix features are a real gap in the feature set — not used here, not evaluated
  • Decision-support only — inspect high-confidence rows manually before acting; do not treat this queue as an auto-publish or auto-deprioritize signal

Ranked Recommendations

Action playbook (149,497 pages scored):

  1. Refresh — 74,467 pages: stale-but-visible or declining-with-demand pages. The largest single category; review this cycle, starting with high-confidence rows.
  2. Refresh and review CTR — 43,790 pages: visible, well-positioned, but under-clicking — check metadata/snippet before a full content rewrite.
  3. Monitor — 19,486 pages: no action needed this cycle.
  4. Refresh and review engagement — 11,236 pages: getting sessions but low engagement/scroll — check on-page experience, not just content.
  5. Expand and refresh — 518 pages: thin content still getting visible impressions. Smallest category, but likely the highest-leverage per page, since these are narrower, well-defined content-expansion tasks rather than a full rewrite.

Confidence split across all 149,497 pages: 17,546 high, 57,203 medium, 74,748 low. With 74,467 pages flagged for refresh but only 17,546 total rows at high confidence, most of the refresh queue needs human judgment before acting — this is a starting point for triage, not a ready-to-execute list. A practical first pass: cross-reference the refresh action with high confidence specifically, rather than acting on either column alone.
